## 一、现状诊断（为什么要重做）

现有 `src/components/game/CombatP5.tsx`（383 行）+ `CombatP5.css`（367 行）是
`absolute inset:0 z-40` 的全屏覆盖层，四张 693×1149 正面站姿立绘，敌人无资产走剪影兜底。

| # | 问题 | 证据 |
|---|---|---|
| 1 | **全员不在场，语法其实是 1v1 格斗** | 代码注释自称"P5 式：一次只展现当前行动者"。P5 是四人始终在场，换手换的是镜头。旧版 `battle-desktop-select.png`（四人在场带尺度阶梯）反而更接近 |
| 2 | **没有地面、没有地平线** | 只有脚下一块椭圆投影，底下没有"地"。没有地面参照物，尺度阶梯读不出来 |
| 3 | **敌人是右上角一张信息卡** | 剪影与行动者之间只有装饰关系，没有空间关系 |
| 4 | **镜头从不移动** | 斩击线/伤害数字/震动/爆闪全叠在同一固定机位，本质是贴纸动画 |
| 5 | **张力最高的元素是装饰红带** | 玩家本人的选择（底部 146px 通用按钮条）最不显眼 |
| 6 | **解放只有一行 log** | 本作最像 Persona 觉醒的高光，现在只有 `setTransformed(true)` |
| 7 | **竖屏构图塌掉** | 390×844 时立绘与敌方剪影落在同一纵轴互相压叠；三处媒体查询硬编码构图 |

## 二、技术路线：伪3D 怎么做

### 2.1 三条路与选择

| 路线 | 做法 | 判断 |
|---|---|---|
| A 真 CSS 3D | `perspective` + `preserve-3d` 搭真舞台 | **只用于 L2 地面** |
| B 手写投影的 2.5D | 实体仍是 2D DOM，投影函数算 `left/bottom/scale/blur` | **主体** |
| C 版面 + 透视线索 | 2D + 收敛/阶梯/机位剪辑 | 语言全保留，单独用不够 |

**选 B 的硬理由**：项目里目前一处 `perspective` / `preserve-3d` 都没有，而这套 UI 大量使用
`filter: drop-shadow`、`mix-blend-mode`、`overflow: hidden`——**这些会强制压平 3D 上下文**。
走 A 得先把整套材质重写。B 让实体继续是普通 DOM，现有美术手段全部保留。

**B 的真正收益**：运镜变成只改一个相机对象，所有实体的 `left/bottom/scale/blur/影子` 都是它的
函数。一次 transition 或一个 rAF tween 就是一次镜头运动——这是现在完全不存在的能力。

### 2.2 世界坐标系

- 单位：**1 世界单位 = 1 个身位**（角色身高 ≈ 1.8 单位）
- `x` 左右，`0` = 画面中轴
- `z` 纵深，`0` = 相机平面，越大越远
- 地面是 `y = 0` 的平面

### 2.3 相机

```
camera = { x, z, height, fov, pitch }
```

- `x` / `z`：机位在水平面的位置
- `height`：机位高度——**竖屏靠它抬高做俯视**
- `fov`：视野（等价焦距，控制整体尺度）
- `pitch`：俯仰——竖屏压平、横屏平行

**已锁机位：肩后追随**（行动者在前景偏下，敌人在正前上方）。

### 2.4 投影（billboard）

实体在世界空间，**菜单与伤害数字在屏幕空间**。世界空间与屏幕空间混用本身就是伪3D 的关键
（P5 的菜单也是屏幕空间的）。

```
depth   = z - camera.z
s       = fov / depth                       // 深度尺度
screenX = 50% + (x - camera.x) * s
scale   = s / s_ref                          // 相对于基准深度
blur    = clamp((z - focusZ) * kBlur, 0, maxBlur)
zIndex  = round(-z * 100)                    // 手动遮挡排序，不用自动 z-sort
```

脚底落点由地面平面投影得出（`y = 0`，含 `height` 与 `pitch`）。
**地平线位置只由 `pitch` 与 `fov` 决定，与相机高度无关**——所以"地平线钉在 42%"这件事
靠调 `pitch`/`fov` 实现，竖屏改 `height` 不会把地平线带跑。

### 2.5 分层与视差

```
L0 天际线 / 霓虹雾
L1 地平线
L2 地面网格（SVG，按投影坐标画）
L3 敌方阵               z ≈ 6.3 – 7.1
L4 我方阵               z ≈ 3.05 – 4.45
L5 前景遮挡             （单位之上、名条之下）
L6 FX  速度线/半调/斩击/碎片   （屏幕空间）
L7 HUD                  （屏幕空间，不参与投影）
```

> **实装时的偏离（S1）**：原方案写"L2 是唯一用真 perspective 的地方"，实装改成
> **用投影函数算出坐标、交给 SVG 画线**。理由是硬伤：CSS perspective 是第二套 3D 模型，
> 它和投影算出的脚底落点**无法保证一致**，而"脚浮在地面之外"这种错位靠眼睛极难发现。
> SVG 直接吃 `project()` 的输出，只有一个真相。代价是失去"真 3D 变换"；
> 收益是不会错位，且完全绕开 WebKit 的 preserve-3d flattening 风险。

### 2.6 比例自适应（不做 letterbox）

世界单位恒定，比例变化时只调相机：

- `tanHalfFovY` 由"最前排角色该占多高"定；竖屏再退到 `MIN_TAN_HALF_FOV_X / aspect`
- `pitch` 由**目标地平线位置**反解（地平线只由 pitch 与竖直视野决定，与相机高度无关）
- `height` 由**目标脚底落点**反解（对 h 是一次方程，不用迭代）

**一套公式服务 1440×900 / 390×844 / 844×390 / 320×568，一条媒体查询都不需要**，
替掉了原来三处硬编码构图。

### 2.7 编队：**必须按屏幕位置反解世界坐标**

这是 S1 最贵的一个坑。最初把编队直接写在世界坐标里，结果：

```
前排 x=-0.75 / z=3.30  →  屏幕横向偏移 -13.06%
后排 x=-0.95 / z=4.45  →  屏幕横向偏移 -12.36%   ← 几乎同列，后排被前排整个吃掉
```

更远的纵深刚好抵消了更大的横向偏移。所以阵型改用**屏幕横向比例 `sx` 定义**，
再由 `worldXFromScreen()` 反解世界 x（`battle/stage.ts`）。深度 `z` 只负责
尺度阶梯与空气透视。代价是世界坐标随宽高比变（竖屏阵型物理上更窄），但屏幕构图恒定。

**实测落点**（`魔都/scripts/verify-battle-stage.ts`，四种比例全部通过）：

```
地平线                42%          （±0.01%）
我方脚底落点          74.9% – 89.5%
敌方脚底落点          62.8% – 65.5%
敌我脚底间隙          9.5%         （要求 ≥ 6%）
我方同深度互不重叠    通过
宽屏敌我身体重叠      0%
```

> 原方案写的"敌方脚下落点 46–54%"是**没算过的估值，实际到不了**：单张地面平面上，
> 脚底要到 50% 需要敌人比前排远约 10 倍，那样它会小到看不见。真正的不变量是
> "敌我脚底不重叠"，而不是某个具体百分比。

窄屏兜底 `fitSlotSx()`：按**身体**半宽把站位夹回画面内（竖屏下队员 0 会跑到 −5.3%、
boss 到 104.2%）。透明画布溢出无妨，身体溢出不行。

### 2.7.1 我方是一个**紧凑的群**（看过效果之后改的）

第一版阵型为了"给敌人让位"，把四个人沿屏宽铺开到了 **61%**——最右边那位像是掉队出画了。
这是把"避让"当成了构图，方向就错了。正确的读法是：

> 四个人**肩并肩站成一个紧凑的群**，被选中的那位前踏一步到"第一位"，
> **其余人按原顺序往前补一格**（整队挪动，不留空洞，也不是把谁单独拉出去）。

`partyFormation(activeIndex, size)` 就是这个：行动者拿 `ACTIVE_SLOT`，其余人按 rank 依次
填 `PARTY_CLUSTER`。所以"选谁"改变的是整队的排布，而不是把某个人拽到远处。

**实测（四种比例）**：

```
                群跨度    最大空隙    脚底间隙
桌面 1440×900    45.7%     4.8%      10.6%
竖屏 390×844     53.6%     0%        10.6%
横屏 844×390     42.8%     8.3%      10.6%
极窄 320×568     51.2%     0%        10.6%
```

两条写进断言的防回归规则：

- **跨度上限**：宽屏 ≤ 50%、窄屏 ≤ 60%。
- **缝隙上限**：≤ **1.8 个身宽**，不是绝对百分比。

> 缝隙为什么用相对身宽判：超宽屏上人物本来就窄（横屏身体只占 6%），同一个阵型算出来的
> 绝对缝隙自然更大——第一版拿"≤ 6%"这个绝对数判，横屏 8.3% 就被判死了，而那个构图其实
> 是对的。**绝对像素/百分比阈值在跨比例的场景里基本都是错的。**

### 2.7.2 目标锁定（本轮一并做了）

原来只有一个共享血池，打击特效与受击永远挂在 `index 0` 上——等于锁死了第一个目标。
现在：

- 每个敌人**各自记血**（`StageEnemy.hp/maxHp`）
- **点场上那个敌人**即锁定，锁定框（`.mato-bs__reticle`）加粗且**不吃空气透视的 blur**
- 锁定目标倒了自动顺位到下一个站着的，不用玩家手动再点
- 非锁定目标的名条缩一号、暗一档，但**仍然显示残血**——不然没法比较该打谁
- 竖屏只保留锁定目标的名条（其余会互相压叠，且不可点）

**总血量怎么摊到多体**：`splitHp()` —— **威胁等级决定总血量，体数只决定怎么分**
（余数记在第一体）。所以"低危 ×3"和原来"低危 ×1"的总血量一致，
改体数不会偷偷改难度。这条是规则侧的约定，S5 做数值时按它走。

### 2.8 四条容易翻车的实现约定（S1/S4 都踩过）

1. **遮挡排序只能有一个基数。** 我方与敌方各用一个基数（敌方 300 / 我方 200）时，
   深度大的一方减掉的少 → **远处的敌人被画在近处队友之上**，整套纵深当场失效。
   统一走 `stackIndex(depth)`。
2. **定位用的 `translateX(-50%)` 不能和动画写在同一元素上。** 入场/受击关键帧里带
   `transform`，会把居中位移一起清掉，敌人横向跳半个体宽。**定位一层、动画一层。**
   同理，居中用独立的 `translate` 属性时，动画里写 `transform: rotate/scale` 是安全的。
3. **入场动画与受击动画必须分两层。** 挂在同一元素上时，切换 `data-hit` 会把
   `animation` 整个换掉；受击结束把 `data-hit` 摘掉，**入场动画被从头重播**
   （`animation` 一改就重跑），敌人无故闪一下。
   → 外层 `.mato-bs__enemy-enter` 恒定不动，内层 `.mato-bs__enemy-body` 随 tick 切换。
4. **`mix-blend-mode` 只能加在光效层上，不能加在特效根节点上。** 加在根上会把整组
   （**包括伤害数字**）一起拿去和背景 screen 混色，白字被混成发黄的糊块。
   数字是信息，必须硬边高对比。→ 逐层加，数字排除在外。

我方 4 人同向并排会像一排证件照 → **按站位分配水平镜像**（`scaleX(-1)`），廉价且立竿见影。

### 2.9 ⚠️ 一个会**让整个前端起不来**的地雷：别用单字母 `z` 当变量名

`webpack.config.ts` 的 externals 把 `zod` 映射成全局 `z`，而
`unplugin-auto-import` 又注册了 `{ from: 'zod', imports: ['z'] }`。两者一撞：

```
源码里任何一处裸记号 z（哪怕只是 cam.z 这样的属性访问）
  → unplugin 认为是未绑定标识符，注入 import { z } from 'zod'
  → webpack 把 zod 编成外部模块，模块体是 `module.exports = z`
  → 这个模块在 bundle 初始化时求值 → 没有 z 全局的环境直接
     ReferenceError: z is not defined
```

**症状极具误导性**：产物里连一处 zod 调用都没有（`z.object(` 计数为 0），
导入是死的，但光求值引用就炸，**页面白屏、body 只剩 21 字节**。

**后果**：本地裸开 `dist/魔都/index.html` 完全起不来——而项目文档一直声称
"本地无头验收能跑完整条链路"。这道口子比文档写的窄。

**处置**：战斗系统里的世界纵深坐标已从 `z` 全量改名为 `depth`
（`stage.ts` / `formation.ts` / `BattleStage.tsx` / `verify-battle-stage.ts` 共 73 处）。
**新代码别再拿单字母 `z` 当变量名。**

**顺带**：这个问题也说明本地自检链路此前是断的。已补两个探针：
`scripts/diag-boot.mjs`（页面到底起没起来 + 控制台异常）与
`scripts/diag-fx.mjs`（命中特效的 mask 有没有真的生效）。

## 三、立绘差分规格

**已确认可补差分**，这是整个演出层级的天花板。693×1149 在两种比例下全程**缩小使用**
（桌面约 0.55 倍、竖屏约 0.4 倍），**分辨率不是瓶颈，姿势才是**。

| 优先级 | 姿势 | 用途 | 张数 |
|---|---|---|---|
| **P0** | 背姿（背对镜头） | 肩后机位的主角 | 4 |
| **P1** | 攻击（挥击/施法） | 打击感成立的前提 | 4 |
| **P2** | 受击（后仰/捂身） | 受击反馈 | 4 |
| **P3** | 解放姿态 | 全屏 cut-in 高光 | 4 |
| P4 | 倒地 / 伏地 | 减员演出 | 4 |
| P5 | 背侧 3/4 | 后排待机的自然度 | 4 |

**P0+P1 共 8 张 = 最小可行集**（有这两级，伪3D 与打击感同时成立）。
P2+P3 是质量跃迁，P4/P5 是磨光。**每一级都能独立停下。**

### 三条不守就一定抖的铁律

1. **同一画布、同一脚底基线、身高一致。** 脚底 y 必须完全一致，否则换姿势时角色会"跳"。
2. **透明背景，不要画投影与地面。** 投影由 CSS 按光源与深度生成；图上带影子会变成两个影子。
3. 不要预乘缩放（避免半透明边缘发黑）。

### 命名与对齐

- 命名 `{角色}_{姿势}.png`，前端查表——与 `src/data/art.ts` 同构，**组件不用动**。
- 站姿沿用 693×1149；解放/特写建议 ≥1200 宽（要全屏裁切放大）。
- **对齐策略：统一画布 + 前端只读 alpha 包围盒做校验（只报警，不修正）。**
  运行时不插手，避免把"刻意伏地/后仰"当成错位修掉。

## 四、敌方：程序化暗影生物

`src/data/enemies.ts` 的 `art` 全空，现在走剪影兜底。伪3D 要求敌人**站位**，否则镜头推过去没有对象。

丑鬼本来就是暗影质魔物 → 程序化生成（不规则 blob + 内部辉光 + 呼吸形变 + 可碎裂）
既补上资产空缺，又比一张贴图更适合伪3D：

- **可以成群**（P5 的敌人从来是一组）
- **可以真的碎**：clip-path 多边形碎片 + 飞出 + 淡出
- 按威胁等级改变体量与变体
- 以后有正式立绘，往 `art` 里填即可，舞台结构不动

### 数量来源

**威胁等级推导 + 标签可显式覆盖**（AI 只给敌人名与数量，弱点/伤害/气力全由前端数据表权威）：

| 威胁 | 默认体数 |
|---|---|
| low | 3 |
| mid | 2 |
| high | 2（实装时按平衡可调） |
| boss | 1 |

覆盖语法：`[battle:丑鬼×3]`（向后兼容，纯名字仍然有效）。
`src/scriptParser.ts` 的 `BATTLE_TAG_RE` 需要扩展，且**必须保持"只认正文尾部"的约束**
（正文中段的示例标签不该把玩家踢进战斗）。

## 五、运镜事件表与两档节奏

**已锁节奏：常态轻运镜 0.2–0.4s ／ 关键动作重 cut-in 0.8–1.5s。**

| 事件 | 镜头动作 | 档位 |
|---|---|---|
| 入场 | 低位仰角拉起，同伴剪影先入画，敌人最后显形（~1.2s） | 重 |
| 换手 | 沿横轴平移锁定该员，其余人退到焦外（blur），该员前踏 + 名牌斜切划入 | 轻 |
| 指令悬停 | `fov −4%` 微推 + 敌方红框脉冲 | 轻 |
| 攻击 | 向敌推进 + 我方前冲位移 + 残影 | 轻 |
| **命中** | hit-stop 定格 70ms → zoom punch（`fov +18%` 回弹）+ 震动 + 全屏斜切特写条 | 重 |
| 敌方回合 | 越过肩后的反向机位，敌方蓄力 → 砸下 → 切回 | 轻/重 |
| 解放 | 全屏 cut-in：半调 + 立绘放大裁切 + 粗斜体招式名，镜头绕轴转 | 重 |
| 收尾 | 镜头拉远、地面网格熄灭、结算板斜切压入 | 重 |

**两档不再靠拍脑袋分，而是由规则事件驱动**：普通出手＝轻运镜，弱点/追加/解放＝重 cut-in。

## 六、打击感：我们没有动作帧

四张立绘是静态站姿，**没有攻击帧/受击帧/跑动帧**。P5 的打击感七成来自角色动画，这条路堵死。

**替代方案：漫画式动作——用剪辑替代动画。**

- 位移代替挥击（前冲 + 尺度突变 + 2–3 层残影）
- 命中瞬间切成**全屏斜切特写**（同一张立绘放大裁切 + 半调 + 速度线），再切回广角
- 敌方暗影生物真的"碎"（多边形碎片飞散）
- **hit-stop 定格必须有**——它是"重量"的唯一来源

第 P1 级差分（攻击姿态）到位后，这套从"纯剪辑"升级为"有前摇的动作剪辑"。

### 6.1 S4 实装：出手时间线

```
  0ms          前摇：行动者后仰蓄力（还没接触）
  100ms        接触：伤害结算 + 命中特效 + 推镜 + 震屏 + 定格
  100→860ms    收势：特效散尽，交还指挥权（或转敌方回合）
```

**为什么把结算推到 100ms**：原来是"按下即结算"，特效跟人物动作同一帧起，读起来像贴纸。
**前摇那 100ms 是打击感的成本，省不掉。** 突进的关键帧在 22% 接触，0.5s × 22% = 110ms，
和 `DASH_MS = 100` 对齐。

**定格（hit-stop）不是全局暂停动画**，而是**烤进关键帧的保持窗口**
（每条关键帧都有 6%→22% 的"保持段"）。全局 `animation-play-state` 要跟一堆动画抢控制权，
时序很容易乱；保持窗口天然和动画同步。

### 6.2 S4 实装：特效分层

一记命中 = **平面图形层 + 位图层**，分工明确：

| 层 | 内容 | 来源 |
|---|---|---|
| 平面 | 放射速度线（`repeating-conic-gradient`） | 程序化，矢量，零体积 |
| 平面 | 半调网点（`radial-gradient` 点阵） | 程序化，P5 签名 |
| 位图 | 斩击弧光 ×2（错开 70ms 读成连击） | CC0 mask |
| 位图 | 三道刮痕（重击签名）、冲击波环、电裂、流线 | CC0 mask |
| 数字 | 伤害数字：硬字 + 斜切 + 飞出 | 纯 CSS |

命中角度**由攻击者与目标的位置现算**（横向百分比要乘宽高比才是屏幕真实角度，
否则超宽屏会算得几乎水平），所以刀口总是从挥刀的人那一侧来。

### 6.3 S4 实装：特效素材与体积实测

**素材（两个来源，都合规）**

| 来源 | 内容 | 授权 |
|---|---|---|
| フリー素材サイトギャラリーハウス「赤い斬撃エフェクトAPNGアニメーション」 | **真序列帧**：13 帧 / 429ms / 30fps / 1080×1080 / RGBA | 商用可 · 加工自由 · **免署名** · "作为作品的一部分使用可以" · 禁止直链（必须下载） |

> **这张卡整体是否触及该范畴，需要项目方自行判断**，不要默认没问题。

**体积实测**（strip 横向拼帧，384px 一帧 → 4992×384）

| 档位 | 13 帧合计 | base64 内联 | index.html |
|---|---|---|---|
| 512px | 183 KB | 244 KB | 4650 KB |
| **384px（采用）** | **120 KB** | **152 KB** | **4426 KB** |
| 288px | 72 KB | 96 KB | 4375 KB |

序列帧的推进方式：`background-size: 1300% 100%` + `background-position-x` 的
`steps(13, end)` 动画，**不逐帧 setState**（30fps 重渲染是白给的开销）。
末值必须写 `108.3333%` 而不是 `100%`——写 100% 的话 steps 的最后一格只到第 12 帧，
**最后一帧永远不会显示**（经典差一错误，见 ImpactFX.css 里的推导）。

### 6.4 ⚠️ 教训：**加色柔光 = 廉价**

第一版特效用的是 Kenney 的柔光贴图 + `mix-blend-mode: screen` 叠白色放射线与网点，
俯视看"元素很多"，实际读出来是**手游打击光效**：

- 全是**加色**（screen），没有黑色 → 没有对比
- 全是**软边**（渐变遮罩） → 没有形状
- **没有方向** → 静态柔光贴图无论叠多少层都不可能有信息量
- 底子还是**单帧**，不是动画

第二版推倒重来，换成：

| 层 | 性质 |
|---|---|
| **13 帧真序列帧扫击** | 主角。**动起来**才是关键，这是信息量唯一真正的来源 |
| 3px 纯白刀口线 + 暗红衬底 | 硬边、不透明 |
| 6 条 2px 实速度线 | 少而实，不是一圈渐变辉光 |
| 细冲击波环 / 刮痕 | mask 实色 |
| 伤害数字（白填充 + **近黑描边**） | 不参与任何混色；描边不能用品牌红，红压红等于没有对比度 |

**结论：这一风格下，"贵"来自硬边、高对比、明确方向与真实运动，不来自素材数量或分辨率。**

**已锁：AP 归行动者 + 弱点→追加。接力机制保留。**

## 七·五、主人与奴隶特性（贴原作的核心机制）

### 7.5.1 核心模型

原作里**被解放的是奴隶，主人是*给出*力量的一方**。本项目里：

> **玩家就是奴隶**（`isPlayer: true`，不占立绘位、不在场上）。
> 所以**不需要做"和仓优希"这个角色**——他的生态位被玩家替掉了。

- **战前选定一名主人，整场不变**
- 主人解锁一条「**奴隶特性**」：**触发式被动，不消耗气力，每回合一次**
- 每个角色的奴隶特性**不同轴**，不是同一招换皮

于是循环闭合：

```
战前  选定主人 → 解锁奴隶特性
战中  主人行动 → 特性触发 → 追加/改写效果
战后  该主人给出「奖励」→ 写变量（信赖 / 解放次数）→ 战报注入 → AI 续写
```

**一句话：你选谁当主人，就决定了你这一场怎么打、以及打完会得到什么。**

### 7.5.2 四人的特性必须落在**不同的轴**上

第一版草案把四个人都写成了"追击的变体"（追撃 / 习得 / 范围追击 / 必中追击），
**这是错的**：那样京香的特色就不成立了，四个人只是在同一个机制上调参数。

修正后的四条，各自改的是**伤害管线上的不同一环**：

```
伤害管线：  取基础值 ──► 定目标集合 ──► 逐次结算 ──► 减去减伤 ──► 落地
               ▲              ▲              ▲            ▲
            日万凛          朱朱           京香          宁
```

| 主人 | 桃之能力 | 奴隶特性 | 改写管线哪一环 |
|---|---|---|---|
| 羽前京香 | 无穷之锁 | **追撃**：释放固有技时，对同一目标追加一次等值伤害 | **结算次数** +1 |
| 东日万凛 | 青云之志 | **借力**：有奴隶时输出按**全场最高**计算，且**固有技也不耗气** | **基础值来源** + **费用** |
| 骏河朱朱 | 玉体革命 | **扩散**：单体伤害变为**全体** | **目标集合** |
| 大川村宁 | 一定会找到你 | **破防**：**无视减伤** | **减伤** = 0 |

**这个框架的价值**：以后加角色，不是写函数，而是**在管线的某一环上挂一个修饰器**。
新角色的特性若不属于这四环，说明需要新增一环——那就是一次架构讨论，而不是一次堆代码。

### 7.5.3 已对齐：日万凛的能力名 = 「青云之志」

| 出处 | 名称 |
|---|---|
| 旧代码 `enemies.ts` | `role: '副组长 · 学习'`（**已改**） |
| **采用** | **「青云之志」** |
| 联网检索的旁证 | 「青雲の志」确实作为技能名出现在**另一款游戏（三国大戦スマッシュ）的联动角色**上；未能确认它是否也是原作漫画里的能力名 |

决定：**按项目方设定采用「青云之志」**，`enemies.ts` 已同步修改。
后续 `data/battle/characters.ts`、剧本协议、世界书条目一律以此为准。

> 留个记录：这条最初是"代码写学习、口头说青云之志"的**双源不一致**，
> 靠一次全项目检索才发现只剩一处残留。**设定名不要散落在代码与文档两处**——
> 加角色时把能力名收进单一数据表，是最省事的做法。

### 7.5.4 主人由谁定

- **剧情战**：由正文尾部的 `[battle:敌人]` 标签**指定**（例如"这一战跟京香一起"）
- **战斗演习**：玩家自选
- 两者**共用同一套规则**——教程必须是真规则，否则教了也白教

### 7.5.5 奴隶特性的表现

**第二道命中特效 + 日志一行**，不做全屏 cut-in（每回合都切会很烦）：

```
羽前京香 · 无穷之锁 → 丑鬼 14　｜　追撃 14
```

第二道特效换个角度与色调，读成"连击"而不是"又打了一次"。

### 7.5.6 数据形态

```ts
// data/battle/characters.ts
kyoka: {
  固有技:   'chain-bind',
  奴隶特性: { 触发: 'onSkill', 修饰: { kind: 'echoDamage', ratio: 1 }, 每回合: 1, 耗气: 0 },
}
```

- 触发时机：`onSkill` / `onAttack` / `onGuard` / `onWeakness`（小枚举）
- 修饰器：对应 7.5.2 的四环，加角色时优先复用
- **加角色 = 加一行数据**，不碰战斗组件

## 八、数据面的三个坑（属于本次应清项）

### 8.1 出战名单与角色表不同源

`enemies.ts` 的 `SQUAD` 硬编码四个人，而 `cast.ts` 的 `CAST` 里**只有京香、优希（玩家）、系统**——
**日万凛、朱朱、宁根本不在角色表里**。这三位在剧情正文里说话会走兜底主题色，
而 `art.ts` 又认得她们的立绘。差分到位后，"谁参战"会变成要改两个地方。

**修法**：`CAST` 补齐三人，加参战标记与定位；`SQUAD` 从 `CAST` 派生。

**顺带待决**：**出云天花有立绘，但既不在角色表也不在出战位——她参战吗？**

### 8.2 战斗是世界的孤岛，且输了跟撤退没区别

`App.tsx` 的 `handleBattleExit` 只弹一条通知然后 `setBattle(null)`——胜负对世界零影响。
更要注意 `CombatResult` 里 `'lose'` 与 `'retreat'` 走的是**完全同一条分支**：
打输了剧情照常推进，像无事发生。

**修法**：见第九、十节（MVU 双写 + 战报注入），并把三种结果分开处理。

### 8.3 剧本协议文档没写战斗

`[battle:]` 目前只活在 `src/scriptParser.ts:80-84,294-310` 的注释里，
`docs/剧本协议.md` 一个字都没提——AI 侧没有依据，也没有"结果如何回到正文"的约定。

**修法**：协议文档补一章：标签语法（含 `×N`）、尾部约束、战报回传语义。

## 十、战报注入协议

> **本节是对我最初方案的纠正。** 我曾提议战报走 `/send` 落一层 user 楼——**那是错的**，
> 会污染聊天记录、把系统信息伪装成玩家发言。
> **正解：走 `injectPrompts`，与玩家的新动作同一次生成。**

### 10.1 参考实现（照抄租借男友）

`租借男友/src/state/GameContext.tsx:455-498`：

```js
eventOn(tavern_events.GENERATION_AFTER_COMMANDS, () => {
  // ...组装模式/位置表/天气/扰动...
  injectPrompts([{
    id: 'character-locations',
    position: 'in_chat',
    depth: 0,
    role: 'system',
    content: [modePrompt, table, weatherPrompt, todayDetail, forecastSummary, perturbationPrompt]
               .filter(Boolean).join('\n'),
    should_scan: false,
  }], { once: true });
});
```

**四个参数每个都有讲究：**

| 参数 | 作用 |
|---|---|
| `once: true` | 只作用于本次生成，**聊天记录零污染、不多一层楼** |
| `role:'system'` + `depth:0` | 出现在最贴近本轮的位置，且不与"玩家发言"语义混淆 |
| `should_scan: false` | **不参与世界书/正则扫描** → 约束性规则必须放在常驻世界书条目里 |
| 内容格式 | 【方头括号】标签块拼接（`GameContext.tsx:87-103`） |

**最要紧的是它注入的性质**：`getAllCharacterLocations()` 是前端用日程表算出的**全员位置**，
AI 没有这个信息源。**注入的是"AI 不可能自己知道的结构化事实"。**
战斗战报与之完全同构——战斗发生在前端，AI 全程没看见。

### 10.2 挂点：与玩家的新动作同一次生成

**已锁：战报不做独立发送，也不做"无输入生成"。**

```
战斗结束 → 写 MVU 变量（持久）→ 关闭战斗层
  → 玩家输入下一句动作（"我上前检查她的伤势"）
  → 发消息 → GENERATION_AFTER_COMMANDS
  → 若有【待播报】战果 → 注入【战况回执】(once) → 清标记
  → AI 生成（变量已是新值）→ 落新楼 → 前端跳楼从头播
```

战报**骑在玩家的新动作上**，与租借男友的地点表同构。玩家打完仗总会做点什么，
挂点必然存在——**不需要验 `/trigger` 能否单独触发生成**。

### 10.3 为什么仍要"双写"

`once: true` 是**易失的**：玩家若重 roll 战后正文，注入就没了，AI 会失去战报上下文、
可能写出与判定矛盾的正文。租借男友不会踩到这个坑，因为它的位置**每轮重算、每轮注入**。

所以战报要**从状态推导，而不是当一次性事件**：

| 载体 | 作用 |
|---|---|
| **MVU 变量**（`战报.待播报` + `战果.讨伐记录`） | 持久事实。重 roll 能重建，AI 每轮可从变量读到 |
| **`injectPrompts`（once）** | 瞬时提示。确保这一轮一定看见，且在最新位置 |

租借男友的"地点"其实也是同一结构（变量里有 `状态.当前地点`，每轮又注入一次）——
这不是发明，是照它的结构补齐。

### 10.4 战报内容格式

照 `formatLocationTable` 的块风格 + `formatPerturbationPrompt` 的指令式尾句
（`scenePerturbation.ts:178-194` 也在块尾写"请根据当前地点…不要直接引用本提示中的方向词"）：

```
【战况回执】
结果：胜利｜回合：3｜我方：无减员
敌方：丑鬼×3 已全灭
弱点命中：2 次｜解放：羽前京香 ×1
主角：骏河朱朱（最终击破）
请据此续写战后正文，不要推翻上述判定，不要让已歼灭的敌人重新出现。
```

- **逐回合流水账不注入**（占 prompt 且稀释重点），只存前端战斗记录面板 + 变量里的讨伐记录。
- 尾句是**指令式而非叙述式**——这是约束 AI 不推翻判定的主要手段。
- "不可推翻"这类常驻规则**必须另写一条世界书条目**（因为 `should_scan: false`，
  注入文本自己触发不了世界书）。

### 10.5 数据侧前置改动

## 十二、工程架构

现在 383 行 + 一堆 `later(fn, 620/820/900/520)` 硬编码节拍。再加八种运镜，setTimeout 会立刻
失控（改一个时长要动五处，且无法中途打断）。

```
src/components/game/battle/
  stage.ts       世界坐标 → 屏幕投影（纯函数，可单测）
  camera.ts      相机状态 + tween + 运镜预设（入场/推进/拉远/越肩/回弹）
  timeline.ts    可中断的演出时间轴（串行/并行 + hit-stop）
  formation.ts   编队规则（我方 2-2 / 敌方 1-3 / 脚下落点带 / 镜像分配）
  shadows.ts     程序化暗影生物（体量 / 变体 / 碎片）
  record.ts      BattleRecord 累积 → 战报文本（确定性）
  BattleStage    分层渲染 L0–L5
  BattleCutIn    全屏 cut-in（斜切条 / 半调 / 特写）
  BattleMenu     屏幕空间 HUD
  CombatP5.tsx   只做编排：状态机 + 时间轴调用
src/data/battleSkills.ts   固有技与属性表
src/utils/tavernBridge.ts  加 injectPrompts / GENERATION_AFTER_COMMANDS 守卫包装
```

- 一个 rAF 主循环推进相机 tween（CSS transition 管不了带缓动、带中途改目标的运镜）
- `tavernBridge.ts` 的规矩照守：全项目唯一直接调酒馆全局的地方，每个调用 `typeof` 守卫 + 本地降级
- 无宿主时只记录战报、跳过注入 → `scripts/verify-*.mjs` 才能照跑
- `prefers-reduced-motion` 下运镜降级为硬切（现有媒体查询骨架保留）
- `tavernEventName` 加 `GENERATION_AFTER_COMMANDS` 键

## 十三、性能预算

锐度没问题，但"全员在场 + 3 个敌人 + 焦外模糊"会同时存在十几个带 `filter` 的合成层，
**手机端最贵的就是 `blur`**。

- 焦外只对 **1–2 个**次要角色做模糊，其余用**降饱和 + 压暗**代替（视觉差别极小，开销差一个量级）
- 全屏半调/速度线用 CSS 渐变而非多层 DOM
- 粒子数量设上限，手机端减档

### 已定（可以直接沿用，无需重议）

| 项 | 结论 |
|---|---|
| 段粒度 | **一段（一层楼）= 1 个回合** |
| 敌方回合 | **前端按规则结算**（AI 只负责把结果写成正文，不决定敌人动作） |
| 主人 | 战前选定、**整场不变**；剧情战由 `[battle:]` 指定，演习玩家自选 |
| 奴隶特性 | 触发式、不耗气、每回合一次；四人四条**各改伤害管线一环** |
| 费用 | 普通攻击 1 / 防御 1 / **技能 3**；每人每回合 **3 点气力** |
| 主人技能免费 | **日万凛专属**，不是通用规则 |
| 奖励 | 战后事件 → 写变量（信赖 / 解放次数）→ 战报注入 AI |
| 技能 UI | 斜切卡片横排（P5 的 skill 列表形态）；普通攻击与防御不做卡片 |
| 玩家身份 | **玩家即奴隶**，不做"和仓优希"这个角色（不占立绘位） |

四条奴隶特性各自改写伤害管线的**不同一环**，互不重合：

```
取基础值 ──► 定目标集合 ──► 逐次结算 ──► 减去减伤 ──► 落地
    ▲             ▲             ▲            ▲
 日万凛          朱朱          京香          宁
```

| 主人 | 桃之能力 | 奴隶特性 |
|---|---|---|
| 羽前京香 | 无穷之锁 | **追撃**：释放固有技时追加一次等值伤害 |
| 东日万凛 | 青云之志 | **借力**：输出按全场最高算 + 作为主人时固有技不耗气 |
| 骏河朱朱 | 玉体革命 | **扩散**：单体 → 全体 |
| 大川村宁 | 一定会找到你 | **破防**：无视减伤 |
